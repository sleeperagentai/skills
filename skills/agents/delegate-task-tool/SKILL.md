# `delegate_task` tool operating rules

Covers the built-in `delegate_task` MCP tool that spawns fresh subagents in isolated contexts. This is NOT about external agent CLIs (Claude Code, Codex, OpenCode — those have their own skills) and NOT about the broader SDD workflow (`subagent-driven-development`); this is the operational contract of the tool itself.

## When to Use

Load this skill any time you are about to call `delegate_task`, especially before:
- writing a `tasks` array with multiple entries (parallel dispatch),
- passing structured or templated text as `goal` / `context`,
- delegating work whose result you plan to report to the user without further verification.

## Before you dispatch: ground-truth the plan

When a plan cites concrete file paths, line numbers, or symbols the implementer is meant to refactor ("modify `apps/foo/bar.go:241-323`", "replace the Higgsfield fan-out"), verify in the parent that those references actually exist on the plan's declared base BEFORE spawning the first implementer. Plans drift — the base branch moves, a prerequisite feature branch never merged, a file got renamed — and a subagent dispatched against stale ground produces either no-op edits or fabricated code that passes a shallow review and breaks downstream.

Ten-second check in the parent:

```bash
# Does every path the plan calls out exist on the base?
for path in <paths-from-plan>; do
  git -C <repo> cat-file -e origin/<base-branch>:$path 2>/dev/null || echo MISSING: $path
done
# And a sanity grep for the specific symbols/line numbers the plan cites.
git -C <repo> grep -n <symbol> origin/<base-branch> -- <path>
```

If anything comes back MISSING or the symbols aren't at the cited lines, STOP and ask the user to resolve BEFORE touching code. Legitimate resolutions: rebase the plan's base onto the prerequisite work, merge the prerequisite in first, or rewrite the plan from the real base. Do not pick silently — the user owns which branch gets history rewrites.

## Payload rules for `goal` and `context`

1. **Never leave `{name}` / `{placeholder}` curly-brace syntax anywhere in `goal` or `context` text.** The runtime scans for unexpanded template markers and refuses the whole call with `Task N goal contains an unexpanded template marker ('{...}')`. This fires on LITERAL syntax too, not just intentional placeholders: API-doc URL paths like `/history/{prompt_id}`, path-param docs like `POST /api/v1/renders/{id}/cancel`, and format-string examples all trip the guard. Rewrite EVERY `{...}` occurrence — substitute the real value, use an ALL_CAPS bareword (`RENDER_ID`, `PROMPT_ID`, `PROJECT_ID`) that still reads as a slot to the child, or use bracket forms like `<name>` / `:name`. Grep your goal for `{` before dispatching if you pasted API docs into it.
2. **The child sees ONLY `goal` + `context` — nothing from the parent conversation.** Repeat every fact the child needs: absolute repo paths, endpoint shapes, env vars, style/format preferences, verification commands. Do not write "as we discussed" or reference prior turns.
3. **Never put secrets (API keys, tokens, DSNs with passwords) in `goal`/`context`.** They land in the child transcript file and in the parent's summary. Give the child an env var name or a file path to read instead.
4. **State verification in the goal.** "Verify by running X and paste the tail" — otherwise the child self-reports success without proving it. External side effects (uploads, PRs, remote writes) require a verifiable handle (URL, ID, absolute path) that the parent then checks.
5. **Grep for every named symbol/constant/function/table BEFORE you put it in a dispatch brief.** A context that says "use `auth.ScopeProjectsRead`" or "call `store.LatestCaptionPlan`" when the symbol does not yet exist produces silent scope creep: the child will add the symbol rather than stop and ask. The resulting commit lists an unrelated file (a scope constants file, an auth module) that the orchestrator did not plan to touch, and the one-commit-per-task convention leaks dependencies into the wrong PR. If a brief needs a symbol that may not exist yet, state it explicitly — "this constant may not exist; if missing, add it and note it in your deviations" — don't let the child decide silently.

## Parallelism and result timing

1. **Batch independent tasks into one `delegate_task` call** with a multi-entry `tasks` array — that's the parallel dispatch path (max 3 concurrent by default). Sequential `delegate_task` calls run one after another.
2. **When you have >3 subagents' worth of work, batch by 3 and hold the rest for the next round.** The concurrency cap is 3 by default (`delegation.max_concurrent_children`) and passing 4+ tasks in one call is rejected with `Too many tasks: N provided, but max_concurrent_children is 3`. Practical pattern: identify the 3 tasks with disjoint file scopes that unblock the most downstream work, dispatch them, end your turn, and dispatch the remainder as its own batch when at least one of the first three has returned. Do this scoping decision in the parent before dispatch — do NOT ask a subagent to "pick which 3 of these 5" because subagents have no visibility into concurrent siblings and default to accepting the whole list.
2. **Background results arrive between parent turns, never mid-turn.** After dispatching, do work that does NOT depend on the results, then give a one-line status and END THE TURN. Do not `terminal tail -f` the transcript to wait; do not sleep-poll. The result re-enters as its own user message when the batch finishes.
3. **A subagent's "completed" summary is a SELF-REPORT.** If it claims tests pass, files were written, or a service was deployed, verify the artifact yourself before telling the user it succeeded — re-run the test, `ls` the file, curl the endpoint. Especially true for anything involving external side effects.
4. **For parallel read-only reviewers, partition by LAYER, not by file count, and make "read-only" checkable.**
   - One reviewer per architectural layer, for example schema/codegen, runtime libraries, and render/integration plus CI. Each gets its own ARTIFACT file list and CONTRACT, so findings don't overlap and every seam has an owner.
   - Allow temporary repro or property tests inside the repo only if the reviewer deletes them. Require `git status --short` to end clean, and name any pre-existing untracked dirs it should ignore.
   - Concurrent reviewers share one checkout. Give each its own temp-file prefix (for example `zz_review_<layer>_*`). Tell it that sibling reviewers' temp files may show up in `git status` and must be left alone.
   - Ban live-spend paths explicitly (vendor calls, `*_LIVE=1` flags).
   - Pass an `output_schema` with `findings[]` (severity, location, issue, evidence, fix) plus `commands_run`, so results can be reconciled mechanically.
   - Tell each reviewer to append every finding to its own scratch ledger file (`<scratch>/review-<layer>-findings.md`) the moment it is confirmed, and to copy any attack/repro file it wrote into a scratch dir before deleting it from the repo. A reviewer that only reports at the end loses an hour of work to a 429 or iteration cap on its last call; the saved attack files become the fix track's regression tests.
   - Run `git status --short` in the parent after they return. A dirty tree means a reviewer broke the contract — move its stray files to scratch (some attack files are live-dangerous if executed: real network calls, vendor spend), then delete them from the tree.

## Review → fix cycle

1. **Parent writes the ledger before any fixer runs**: one row per finding (`id | severity | location | issue | disposition`) in a file next to the plan. The parent decides every disposition — `FIX track X`, `FIXED <sha>`, `ACCEPTED-with-change`, `DEFERRED → phase N` (amend the plan row in the same edit) — and fixer briefs say "implement the decisions, do not re-argue". A fixer that is allowed to re-litigate a finding spends its budget on the argument.
2. **Group fixes into tracks by file ownership, not by reviewer.** 3-4 items per track, one commit per item, each item carrying the reviewer's repro as a regression test proven to fail before the fix (file swap via `git show HEAD:<file>`, never stash). Point the brief at the saved attack files and flag the ones that must not be executed before the fix lands.
3. **State cross-track ORDERING in the brief** when one track's item consumes another track's API change: "check `git log --oneline -8 -- <path>` first; do the independent items first; if the dependency is still absent at the end, implement against the current API and note it". Without this the dependent child either blocks or reinvents the sibling's change.
4. **The parent takes the orphan items while tracks run** — CI yml module lists, Dockerfile CMDs, doc/pack banners, stale comments — in one `fix(review): …` commit. They are too small to dispatch and no track owns them.
5. **Round 2 re-reviews the fix diff only** (`git diff <pre-fix-sha>..HEAD`), not the whole feature.

## Sizing tasks

- Small, mechanical, single-tool tasks belong in the parent, not a subagent. Delegate when the work is reasoning-heavy, would flood parent context, or is genuinely independent from other in-flight work.
- One subagent per file/module boundary works well for parallel builds. Multiple subagents touching the same file will race and clobber each other.
- **On a large monorepo (Go+TS, multi-package builds), the 50-call cap truncates plans of 9+ tasks even with recon.** Practical per-subagent ceiling is ~3-4 non-trivial tasks WITH pre-loaded reconnaissance, ~2 without. Discovery calls (grep/read/build/goose-up) are cheap individually but stack up: each task in a monorepo is easily 8-15 tool calls (locate, read, edit, build, test, commit, push). Cap a single dispatch at 3-4 tasks max and use a chain of dispatches instead of one giant goal. Count N look-alike artefacts (12 fixture scenes, 9 adapters, 8 golden files) as N items, not one — each still costs its own write + lint + gate + test calls, so "deps + harness + 12 fixtures + a chrome test" is a 15-item brief that truncates with the harness half-built and zero fixtures.
- **For parallel fan-out, put an explicit "do NOT touch" directory list in EACH child's context** naming what its siblings own. Vague coordination ("a sibling is also editing the ai-gateway") is not enough — children each have their own working copy and rebase at commit time, so overlapping edits produce merge conflicts or last-writer-wins clobbers. Assign disjoint directory trees, or route shared-file edits through a separate init/registration file so siblings never edit the same lines.
- **Give each parallel FIX track its own git worktree and branch, cut from the same base commit, instead of a shared checkout.**
  - Create it with `git worktree add -b fix/<track> <absolute scratch path> <base>`.
  - Install dependencies in each worktree (offline and frozen), and copy over any caches the tests need that an install does not produce.
  - Write each brief to a file and point the goal at it. The brief lists owned paths, do-not-touch paths, the evidence and the parent's decision for every item, and the verification commands.
  - Put at most 3-4 items in each brief. That is the same per-subagent ceiling given above. If a track owns more items, write its second brief now and dispatch it later as the finisher in the same worktree. Fix tracks given 6-8 items each all truncate before the last items. A brief whose items are already settled and that pre-loads verified file:line facts can carry 5: the parent decides each item and the child only implements it.
  - Tracks never push, merge or rebase; the parent merges the track branches afterwards.
  - While tracks run, the parent edits only files no track owns. An item found later in an owned file goes to that track: by steer if its brief is still under the cap, otherwise into its next brief.
  - Merge each track from the parent, one at a time:
    1. Verify the worktree yourself with `git log <base>..HEAD`, `git status --short` and the full suites, including the slow steps (fuzz, cross-language parity) that a truncated child skips.
    2. Run `git rebase <feature-tip>` inside the worktree so history stays linear, and rerun the suites on the rebased tree.
    3. Run `git merge --ff-only fix/<track>` from the main checkout.
    4. Run `git worktree remove <path> && git branch -d fix/<track>`.
  - A rebase rewrites SHAs. Any ledger or report that cites track commits should name the track until it is merged, then take SHAs from the feature branch's `git log`.
- **For parallel siblings sharing a branch, mandate scoped `git add <paths>` in each child's context — ban `git add -A` and `git add .`.** Even for a SINGLE implementer in a repo that has untracked workspace files (docs the user left in the worktree, lockfiles, local-only dotfiles like `.claude/`, build artifacts like `apps/*/cli`), a sweep-everything add quietly bundles them into the task's commit and leaks them into the PR. Either tell the implementer the exact paths to stage (list them in `context`), or tell it to `git status --short` first and `git add` only the files it touched for this task. For parallel-sibling scenarios the same ban applies for a second reason: after a `git pull --rebase` folds in the sibling's commits, the sibling's earlier uncommitted work-in-progress can still be present in the child's working tree (rebase-in-progress files, files the sibling wrote but hadn't yet committed when the rebase started) and `-A` will happily commit those under the wrong author with the wrong message.
- **Spot-check `git show --stat HEAD` in the parent after each implementer commit.** One line does it: `git show --stat <sha> | grep '|' | grep -v '<owned-path-1>\|<owned-path-2>'` prints every file outside the child's ownership list (empty = clean); then re-run the child's verify command in the parent. The subagent reports `3 files changed` from its own summary but reality is 8 files once untracked workspace litter got swept in. Catch it immediately: `git reset --soft HEAD~1`, `git restore --staged <stray>`, re-commit cleanly. Fixing the first dirty commit is cheap; letting a chain of them pile up before PR time is not.
- **Ban whole-region reformatting outside the intended diff in the dispatch brief.** When an implementer edits a non-trivial existing file, a repo-wide formatter run (`goimports -w`, `gofmt -w`, `prettier --write`, `ruff format`) will reshuffle imports and re-align structs in regions the task did not functionally change — that cosmetic churn then lands in the commit and is indistinguishable from real work at review time. State it explicitly: "Do NOT reformat regions you did not functionally change. If `goimports -w` / `gofmt -w` reshuffles imports or re-aligns structs in untouched code, revert those regions with `git checkout HEAD -- <file>` and re-apply only your real lines via patch before you commit." Recovery when it already landed: `git stash push --keep-index --include-untracked -- <file>`, `git checkout HEAD -- <file>`, re-patch only the intended lines, `git stash drop`. Alternatively `git reset --soft HEAD~1` + selective re-add, then re-commit — whichever leaves the smallest diff.

## Commit before verify

When a subagent's `goal` bundles code changes + build + E2E verification + `git commit && push`, order it as **build/typecheck → commit → E2E → follow-up commit for verification artifacts**, not one commit at the very end. Iteration caps and timeouts most often fire during the slow E2E step (server boot, seeded data, sha256 diffs) — if the commit is last, a truncation loses all the code and forces a finisher dispatch to re-serialize the on-disk work. State it explicitly: "After `pnpm typecheck && pnpm build` pass, git add + commit + push the code changes. THEN run the E2E and append a second commit with any verification outputs." A first commit that's already pushed is cheap to amend or extend; no commit at all after 50 iterations is expensive to recover.

## Commit messages and PR bodies ride in via `-F` / `--body-file`

Multi-line commit messages and PR bodies with backticks, `$`, pipes, embedded code fences, or heredoc markers break shell quoting when passed inline to `git commit -m` or `gh pr create --body`. The failure mode is cryptic (`unexpected EOF while looking for matching \`\``, `syntax error: unexpected end of file`) and a child will burn iterations retrying variants of the same escape rather than switching strategy. Instruct the child in `context`: write the message to a scratch file (`$BH_AGENT_WORKSPACE/commit-<name>.txt` or `/tmp/`), then `git commit -F <path>` and `gh pr create --body-file <path>`. This is a workflow rule, not a shell-quoting lesson — state it before the first commit, not after the first failure.

## Split wide refactors into sequential sub-PRs

A refactor that touches many call-sites plus a migration plus typed wiring plus adapter changes plus a pilot does not finish inside one subagent's 50-iteration budget, and will not pass review as one PR either. Split at natural layers before dispatching anything:

- **PR A** — plumbing: new module, interface change, provider/adapter wires. Pure additions, zero behaviour change for existing callers.
- **PR B** — data layer: migration, store methods, DB-backed implementation of the interface.
- **PR C** — callers: rewrite each call-site onto the new interface, seed-time behaviour, pilot adapter.

Each sub-PR merges green and reviewable alone. Spawn one subagent per sub-PR; the next's context references the previous's merged SHA as its starting state, which keeps individual dispatches small enough to finish. This is a scoping decision in the parent BEFORE the first dispatch — asking a subagent to "split this plan into sub-PRs then execute" conflates planning and execution and almost always truncates mid-PR-A.

The shape of a refactor that NEEDS this split: 5+ call-sites OR (a migration + >3 call-sites) OR (a new interface + adapter wires + >2 call-sites). The shape that does NOT: a single-file refactor, a one-package rename, anything whose diff would fit on one review screen.

## Pitfalls

- **A truncated child often leaves its last item written but unverified.** Before re-dispatching, run its typecheck and tests in the parent. If they are green, prove each new test fails on the old code by swapping the file (see the stash bullet below), then commit from the parent. That costs 3-5 calls; a re-dispatch costs a whole child.
- **Don't tell a subagent to `kanban_complete` a task in the parent's queue** — children cannot close tracked work, they return findings and the parent applies the transition.
- **Don't rely on child-side working directory persistence between calls** — each subagent gets its own terminal session. If a later dispatch needs the same repo, put the absolute path in its `context`.
- **A task-cap or timeout in the child terminates it early with `interrupted`; partial output still returns.** Read the partial output before re-dispatching — sometimes the useful work already landed and only verification remains.
- **The shape of the self-report itself diagnoses truncation even when the `TRUNCATED` marker is absent or weak.** A completed-status report whose `commit_sha` is empty string, whose `test_output_summary` says things like "Prior session output not retained" or "please re-run verification", or whose `deviations` admits "final response was rejected by validator; resubmitting", or whose per-item list leaves out items the brief assigned, means the child ran out of iterations and salvaged a shape-valid report rather than reporting actual outcomes. Do NOT trust that report — `git status --short` + `git log --oneline <parent>..HEAD` + `git diff --stat` in the parent to see what actually landed, then either finish inline (small) or dispatch a scoped finisher (large) using the real on-disk state as the baseline.
- **When a fan-out subagent hits `max_iterations` (TRUNCATED) with uncommitted work on disk, dispatch a small focused FINISHER scoped to committing/wiring, not the whole original task.** Re-running the full goal wastes iterations re-doing landed work and often diverges from the on-disk state. Instead: `git status` in the parent to see what's uncommitted, then delegate a narrow "commit files A/B/C, add missing wiring in D, run verification E, push" task that trusts the existing on-disk work.
- **If the same brief shape truncates a SECOND time after a scoped finisher dispatch, stop re-dispatching that shape and split along the natural architectural seam.** Two truncations in a row on "Part A + Part B + Part C" means the brief is wrong, not the subagent — the cognitive load of three concurrent architectural concerns (new type + new API path + new tests, or worker-side + API-side + test wiring) exceeds the iteration budget regardless of pre-loaded recon. Commit whatever landed from the second attempt in the parent, then dispatch each remaining layer as its own single-commit brief (worker-side commit now, API-side commit as a follow-up dispatch). A third truncation on the same shape is a planning failure, not a sizing failure — do not retry.
- **Pre-load reconnaissance into the follow-up's `context` when resuming a truncated fan-out.** The first subagent burns iterations grepping for scope constants, function locations, existing schema columns, and store method signatures; a finisher for the remaining tasks that inlines those findings (exact file paths, `line N` anchors, existing const names, verbatim code sketches, and any assumptions from the plan that turned out wrong on inspection) executes rather than re-explores and lands ~2× the tasks per iteration budget. Grep in the parent between dispatches; the parent's grep calls are cheap, the child's are expensive. State explicitly in the context: "Do NOT re-explore what's documented here" — without that clause children still spend calls verifying pre-loaded findings.
- **When a truncated subagent leaves ONE small file uncommitted (< ~250 lines of straightforward glue), finish it in the parent instead of dispatching another child.** A whole subagent turn spins up a fresh terminal, reloads skills, greps for context it needs, then writes the file — easily 8-15 tool calls. The parent already knows the surrounding types, the API-client name, and the reducer shape from prior turns; writing the file directly costs 3-5 tool calls (read siblings for type signatures, write_file, typecheck, commit, push). Reserve dispatches for work that genuinely needs a fresh context window or is truly independent of parent state.
- **When a truncated child leaves the infrastructure but none of the N look-alike consumers (fixtures, adapters, scenes), write ONE consumer in the parent to prove the chain end to end, commit infra + that one, then dispatch the remaining N−1 as a pure-production brief that names it as the reference file.** Proving the chain in the parent (typecheck, lint, gate, bundle, render) surfaces the infra bugs — alias resolution, an exports map that hides `package.json`, a lint rule that rejects a prop name — that would otherwise eat the finisher's budget one at a time, and it hands the next child a working template to copy instead of a spec to interpret.
- **When a truncated subagent leaves MANY files uncommitted spanning multiple plan tasks, commit each task's files as its own commit using the plan's exact commit message — not one `git add -A` blob.** A single omnibus commit hides which task landed cleanly, defeats bisect on the follow-up bugs, and forces later reviewers to reconstruct the task boundaries from the diff. Read the plan's commit-message list, group the uncommitted files against it (`git status --short`), and `git add <files-for-task-N> && git commit -m "<plan message for N>"` in a loop. One push at the end is fine.
- **Before dispatching into a shared checkout, look for other live workers (`git worktree list`, `ls .worktrees`, `ps -eo etime,command | grep -i hermes`) and treat their paths as foreign in every brief and in the parent.** A kanban/cron worker sharing the repo can stage files into the SAME index mid-task: run `git diff --cached --stat` before every parent commit, `git restore --staged <foreign path>` to unstage without touching the disk, and never `git add -A`. It also shares the machine's Chrome, so a chrome/render test that fails once and passes on rerun is contention, not a regression — rerun once before investigating. Name the foreign untracked dirs explicitly in each child's never-touch/never-stage/never-stash list.
- **Before finishing inline after a truncated fan-out, run `git stash list` and pop any `unrelated-wip`-style stash first.** Parallel siblings sometimes stash conflicting or unrelated working-tree changes to a named stash before rebasing or committing (e.g. an ai-gateway factory edit while a sibling committed to services/db). If the parent commits without popping, that work is orphaned in the stash and silently omitted from the branch. Read `git stash list` first (each entry says `On <branch>`) and pop the entry by its explicit ref. The stash is shared by every worktree of the repository and often holds other branches' WIP, so a blind `git stash pop stash@{0}` can apply the wrong branch's work. For the same reason, tell children working in sibling worktrees not to use `git stash` at all. While worktrees are live, the parent should not stash either when proving that a test fails without a fix. Swap the file instead: `cp f <scratch>`, then `git show HEAD:f > f`, run the test, and restore with `cp <scratch> f`. Keep parent probe scripts strictly read-only: a `git stash -q` pasted into a status probe hides the whole uncommitted tree and the next `git status` reads clean; if it happens, `git stash pop` the entry you just created before running anything else.
- **When discovery reveals the plan assumed deps that don't exist, authorise a REDUCED scope in the finisher rather than telling the child to invent scaffolding.** Plans written from a PRD often name activities, endpoints, or infrastructure that hasn't been built yet ("call TTSActivity", "query /api/v1/voices"). A child instructed to "implement Task N" will either invent Temporal activities that don't fit the workflow shape or burn iterations building infrastructure the plan didn't budget for. Instead, in the finisher's context: rewrite Task N's scope explicitly ("REVISED Task N scope — do THIS, not the original"), stub the missing dep with an empty field and a TODO comment, and record the deferred work as a follow-up in the commit message. A working stub that compiles beats a half-built activity that doesn't.
- **Verify the plan's data-model assumptions against actual migrations before dispatching.** Plans often assume a column is missing when the initial schema already provides it (a `role` column, a nullable FK, a timestamp) — the child then writes a redundant migration or a wrong role vocabulary. Grep the initial schema migration for the target table in the parent, restate the real column shape in the child's context, and delete now-unneeded migration tasks from the goal.
- **A batch of 2-3 concurrent subagents can 429 collectively against the same provider account, and the whole batch fails together.** Anthropic (and similar tier-limited providers) count concurrent requests against a shared workspace or account bucket, not per-child; a parallel dispatch that fits under Hermes's concurrency cap can still exceed the provider's per-minute or per-hour usage limit. Recovery: read the reset timestamp from the error message (Hermes surfaces it as "Limit resets at HH:MM (in Xm)"), do OTHER work in the parent until that time passes, then redispatch — do NOT retry immediately (bucket is still saturated), do NOT serialize the same batch inside the same window (same bucket). If the reset is >20 min away and the work is urgent, switch models with a per-task `model`/`provider` override on the retry. Better: pin fan-out children to a different model than the parent from the FIRST dispatch (parent on an Opus-class model, children `model: "claude-sonnet-4-5"`, `provider: "anthropic"`) — provider buckets are per model, so three children stop competing with the parent's own calls; it reduces, not eliminates, 429s on hour-long children. Before the redispatch, salvage what the dead children left: `git status --short` shows their untracked/partial files; make them self-consistent from the parent (run the child's own sync/check script, fill placeholders) and append a `## RE-RUN NOTE (read first)` section to the SAME brief file listing exactly what exists on disk and must be kept, so the retry resumes instead of rewriting. Redispatch with fewer concurrent children than the batch that tripped the limit.
- **When the user asks for intermediate visibility on a long fan-out ("start the server so I can see progress", "show me what's built so far"), STEER a running child to land the scaffold + one working example FIRST with a commit-push, before continuing the full inventory.** Otherwise the user waits the full subagent lifetime with nothing to look at, and the child's mid-run summary is not viewable by the user. `delegate_task(action="steer", subagent_id=..., message="NEW ORDER: land the Storybook scaffold + one Button component + commit-push FIRST, THEN continue the rest of the inventory.")` — the steer arrives at the child's next tool-result boundary and re-orders its plan. Ship the smallest viewable thing first; iterate from there.
- **A subagent's final report is a snapshot from BEFORE its terminal message hit the parent — parallel siblings may have already landed some or all of the described uncommitted work.** When a report says "X files uncommitted, needs cleanup" or "the pricing page has an unrelated typecheck failure I couldn't finish fixing", verify with `git status`, `git log --oneline origin/<branch>..HEAD`, and the failing verification command in the PARENT before dispatching a finisher. Often what the child described as pending is already on origin because a sibling committed it during the reporting window; a finisher dispatched to "clean it up" then re-does or worse re-writes the work.
- **A subagent's claim that a failure is "pre-existing / unrelated to my scope" needs parent-side reproduction before trusting it.** Sometimes the failure is real, was introduced by that child's partial fix, and now blocks the next batch. Rerun the exact verification the child cited (`pnpm typecheck`, `pnpm build`, targeted test) in the parent; read the actual error message. If the child left a half-applied fix (patched one file, hit iteration cap on the follow-on error), inline-complete the fix in the parent — do NOT re-dispatch and hope the child re-derives the same conclusion.
- **When steering a fan-out toward user-visible progress, keep the steer terse and imperative: 3-5 numbered steps ending with "THEN continue as planned".** Long steers get diluted or misprioritised. The steer text appends to the child's next tool result — it competes for attention with real tool output — so leading with the new order ("NEW ORDER:" or "STEER:") and enumerating the reprioritised tasks in 1./2./3. form makes it survive that noisy context.
- **When the user says "stop all subagents", run `action=list`, then `action=stop` on every live id, and do nothing else with their output.** Children halt at their next iteration boundary and the batch still arrives later as an `interrupted` completion message; answer it with a read-only state report (`git log --oneline -3`, `git status --short`, what each child had committed vs left on disk) and wait for the user's next instruction. Do not finish, commit, or discard their partial work on your own — a stop is a reverse signal, not a handoff.
- **Run `action=list` before you steer.** A child that has already finished cannot be steered (`No live subagent`), and a steer queued too late comes back as `missed_steer`. Fold those items into the finisher's brief instead. Better still, put known add-on items in the original brief file rather than steering them in later. Never steer extra items into a child whose brief is already at the 3-4 item cap. Each steered item uses the same call budget, so the child truncates with its original items unfinished.
- **Do deletions in the parent BEFORE dispatching a child whose task starts with `git rm` / `rm -r`.** The terminal's destructive-command guard prompts the user for consent; a subagent has no user to answer, so the command times out as BLOCKED, the guard forbids the child from retrying or achieving the deletion another way, and the whole dispatch is wasted (the child correctly stops rather than half-editing). Pattern: run the batched `git rm` in the parent (answer the consent prompt yourself, or ask the user via clarify when it blocks), confirm the `D` entries in `git status --short`, then dispatch with "deletions are already staged — do NOT run git rm again; if another file must go, report `needs deletion: <path>` as a deviation". Also tell the child to stage with `git add -A -- <owned paths>` so the staged deletions ride in its commit.
- **Read every child's `deviations` list as a design review, not a changelog, and fix contract breaches in the parent before the next dependent dispatch.** A child that cannot satisfy a hard rule (no network, no `fetch`, integer money, one file per module) tends to grant itself a reasoned exception ("the single place a scene calls `fetch`", "mirroring the staticFile-through-props rule") and documents it as if it were the architecture. The next child inherits that doc/pack/test as ground truth and bakes the exception into the gate, so it compounds. Grep the landed artifacts for the forbidden token, restore the invariant by moving the capability to the host side, land a small fixup commit, and update the plan/contract wording in the same commit.
- **When a `clarify` on a design decision times out mid-orchestration, apply the rule the plan already states for that case, write the evidence into the plan in the same commit, and flag the decision as reversible in your status line.** The user stepped away; stalling the dependency chain until they return costs more than a documented, cheap-to-reverse default, and re-asking re-blocks the same chain. Only decisions with no plan rule, and destructive ones, wait.
- **Append a `## RE-RUN NOTE (read first)` to an existing brief file instead of rewriting it when re-dispatching.** Tell the child in `context` to read that note first. The note lists what already exists on disk (keep, do not rewrite), what the parent did in between (deletions staged, bodies synced), and the remaining items; the rest of the brief stays byte-identical, so the verified facts and verify block are not re-derived or drifted by hand.
- **Take a child's findings from its completion message, not from the live transcript log.** The log elides long values (`…(+N chars)`), so its JSON cannot be parsed back out. Copy what the next dispatch needs into its brief file directly.
