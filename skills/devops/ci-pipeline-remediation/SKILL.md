# CI pipeline remediation

## When to Use

- CI is red on `main` for multiple consecutive runs and the workflow is no longer an enforced merge gate.
- A lint tool reports thousands of hits across the codebase and a single auto-format PR would be unreviewable.
- A CI job fails on infra setup (missing binary / missing module / shellout dep not installed in the job) while the same test passes locally.
- Pipeline is green but the job labels (`Node`, `OpenAPI lint + diff`) don't say what they verify.

Not for: writing a CI pipeline from scratch on a greenfield repo (just copy a template), or deep debugging of flaky tests (that's `systematic-debugging`).

## Standing rules

- **Name CI jobs by what they VERIFY, not by the language family alone.** `Web · typecheck + build + biome` beats `Node`; `Go · build + test + vet (arm64)` beats `Go (ubuntu-24.04-arm)`. A human scanning the Checks UI should see what passed, not have to click through to find out.
- **Make CI an actual gate before adding new checks.** A pipeline that's been red for 5+ consecutive runs is decorative, not enforced. Fix existing red jobs before adding more jobs on top — otherwise the next failure is attributed to whoever added the newest check, not to the pre-existing debt.
- **Separate pre-existing failures from your change's failures** by running the full CI command locally against `main` BEFORE touching anything. If the metric to beat is "0 new errors in files I touched" instead of "0 errors overall", you'll know when to admin-merge a PR whose remaining CI red is upstream debt.

## Procedure

### 1. Diagnose: what's actually failing

```bash
# Which jobs are red on main?
gh run list --branch main --workflow <ci-workflow-file> --limit 5
gh run view <latest-failing-run-id> --json jobs -q '.jobs[] | {name, conclusion}'
# Dig into one failure — but filter the log, don't eyeball 10k lines:
gh run view <id> --log-failed 2>&1 | grep -iE 'FAIL|error|Error:' | head -30
```

Classify each failure as:
- **Infra gap** — CI env missing a dep that tests shell out to (e.g. Go test shelling to a Node sidecar; a tool not pre-installed on the runner).
- **Rule backlog** — lint tool reports thousands of style/a11y hits across the real source; recommended ruleset is noisier than the codebase cares about.
- **Real bug** — the lint flagged genuine correctness issues (fallthrough switch, unsafe optional chain, missing path params).
- **Vendored/compiled noise** — lint is running on build output (`dist/`, `storybook-static/`, `.next/cache/`) or vendored docs (`.agents/`, `node_modules/`-adjacent) that should never have been linted.

### 2. Quantify the backlog before fixing

For a lint failure, dump counts by rule:
```bash
# biome
pnpm exec biome check --max-diagnostics=10000 . 2>&1 | grep -oE 'lint/[a-zA-Z0-9/]+' | sort | uniq -c | sort -rn | head -20
# redocly
npx -y @redocly/cli@latest lint <spec> 2>&1 | grep -oE 'Error was generated by the [a-z-]+ rule' | sort | uniq -c | sort -rn
# eslint
npx eslint . --format=json | jq '.[] | .messages[] | .ruleId' | sort | uniq -c | sort -rn
```

If one rule accounts for most of the count, the fix might be "ignore the directory that caused it" (vendored/compiled noise) rather than "fix every hit". Check WHERE the hits concentrate:
```bash
pnpm exec biome check --max-diagnostics=10000 . 2>&1 | grep -oE '^\./[^:]+' | sort | uniq -c | sort -rn | head -20
```
If 99% of hits are in one directory, that directory is almost certainly build output or vendored content — add it to the LINTER'S ignore list (not just `.gitignore`; linters find compiled JS and complain even if git doesn't track it).

### 3. Fix in three strokes, in this order

**Stroke A — ignore the noise.** Add build/vendor dirs to the linter's ignore list. Common offenders: `storybook-static/`, `.next/cache/`, `.agents/`, `**/dist/**`, `**/generated/**`, `**/build/**`, `**/.turbo/**`, Remotion `build/` bundles. For `biome.json`: `files.ignore`. For redocly: not applicable (per-rule config instead).

**Stroke B — fix the real bugs the linter correctly flagged.** The 1-5 real issues hiding under the backlog are the main deliverable of the remediation. In today's biome case: one fallthrough switch missing an explicit `return`, one unsafe optional chain. In today's redocly case: one `DELETE` operation missing path params and responses. These are regressions the project would want fixed regardless of CI pressure.

**Stroke C — demote the stylistic backlog to `warn`.** Rules that trip hundreds of times and represent style/a11y debt (not correctness bugs) get downgraded from `error` to `warn` in the tool config, with a doc comment explaining the migration deferred. The lint still runs, warnings are still visible in diagnostics, but CI doesn't fail. Backlog becomes trackable follow-up work, not a 400-file auto-format PR.

For biome, the pattern is `rules.<category>.<rule>: "warn"`. After `--write` and config changes, `pnpm exec biome check --diagnostic-level=error` shows what's still blocking — should be 0. See `references/lint-tool-demotion-patterns.md` for biome/redocly/eslint/ruff/golangci-lint equivalents.

### 4. Fix infrastructure gaps

A Go test shelling out to a Node sidecar fails on CI with `ERR_MODULE_NOT_FOUND: typescript` because the Go job never ran `pnpm install`. The fix is `pnpm install` as a step in the Go job, before `go test`, even though the Go code itself has no Node dependency. More generally: **a test that works locally because your dev shell has everything installed will fail on a CI runner that only installs what the job explicitly declares.** Trace every `exec.Command`, `subprocess.run`, and shellout in the test tree and ensure its binary/module is set up in the job.

### 5. Verify locally with the EXACT CI commands

Run the full set of commands the CI job runs, in order, from a fresh checkout before pushing:
```bash
go build ./... && go test -race ./...
pnpm turbo run typecheck build
pnpm exec biome check .
npx -y @redocly/cli@latest lint <spec>
```
All must exit 0. If a step passes locally but fails on CI, the next debug step is usually env (missing var, missing binary, OS-specific path).

### 6. Rename jobs if their labels lie

After the pipeline is green, rename each job so its label describes what it verifies. `Node` → `Web · typecheck + build + biome`. `OpenAPI lint + diff` → `OpenAPI · redocly lint` (there is no diff). This is a free pass: `name:` field edits only, zero behavioural change, trivial PR.

## Pitfalls

- **Do NOT run `biome check --write` (or `prettier --write`, `eslint --fix`) as the first step of a lint remediation on a legacy codebase.** It auto-reformats hundreds of files (quote style, import type, template literals, single-var declarator) and generates an unreviewable 50k-line PR. Fix the ignore list and rule demotions FIRST, then only run `--write` after narrowing to a scope you can review. If you accidentally run it, `git checkout --` the whole tree and start over.

- **The LINTER'S ignore list is different from `.gitignore`.** `storybook-static/` can be gitignored and still get linted because biome walks the filesystem, not git. Every linter has its own ignore file or config block — biome: `files.ignore` in `biome.json`; eslint: `.eslintignore` or `ignores`; redocly: not path-based (per-rule); ruff: `exclude` in `pyproject.toml`.

- **Lint rules split cleanly into "real bugs" vs "style/a11y backlog".** The split for biome, roughly: `suspicious/noUnsafeOptionalChaining`, `suspicious/noFallthroughSwitchClause`, `security/*`, `correctness/no*` are real bugs — keep at `error`. `style/*`, `a11y/*`, `complexity/useOptionalChain`, `suspicious/noExplicitAny`, `suspicious/noArrayIndexKey` are style/best-practice — demote to `warn` when the backlog is too large to fix in one PR. The config comment should name the deferred-migration PR so the backlog is visible.

- **`git add -A` sweeps unignored build output and agent scratch directories.** Classic offenders: `packages/*/build/` (Remotion), `.hermes/`, `.next/cache/`, `storybook-static/`. After any `git add -A` or `git add .`, run `git diff --cached --stat | tail -3` — if the total insertion count is wildly larger than your change, something leaked. Fix: `git reset --soft HEAD~1`, add the offending dir to `.gitignore`, `git rm -r --cached <dir>/`, re-commit. See the recovery recipe in `references/git-add-dash-A-leak-recovery.md`.

- **Admin-merging over red CI is correct when the red is pre-existing.** If `main` was failing before your PR and your PR provably didn't contribute to the failure (same jobs red, same error signatures), `gh pr merge --admin` is the right call — waiting for green blocks everyone else and the red is upstream debt, not your regression. Document the admin-merge rationale in the PR body ("Pre-existing failures on main unaffected by this change; see run <id>"). Do NOT admin-merge if your PR introduced ANY new failure, even if "all the real stuff passes".

- **`npx -y @redocly/cli@latest` picks up the latest redocly even if the project pins a version.** Fine for local verification; wrong for CI. Pin the version in the workflow (`npm i -g @redocly/cli@1.34.x`) so lint rule severities don't drift when redocly ships a new release. Same applies to `goose install @latest` — pin the exact version.

- **A `redocly.yaml` demoting rules to `warn` is visible to every developer**, not just CI. Add a header comment explaining what backlog is being deferred and the trigger for cleanup ("PR N will migrate 42-schema nullable backlog to type arrays; drop these demotions after that lands"). Otherwise someone later reads the config and assumes the project genuinely doesn't care about operation-summary.
